# Веб-система снабжения «Ракета»: техническая оценка и план промышленной реализации

Ответ на краткое ТЗ v0.5 от 09.11.2026 (замена Google Sheets: прогноз продаж, остатки,
закупочная потребность, загрузка WB). Документ — взгляд разработчика на архитектуру MVP
заказчика, интеграции и доведение до стабильной эксплуатации. Расчётные формулы и правила
статусов остаются за специалистом по снабжению; здесь — как их надёжно посчитать, сохранить и пересчитать.

---

## 1. Что я считаю главными рисками (и что предлагаю сделать в первую очередь)

| Риск | Почему это больно | Что предлагаю |
|---|---|---|
| **Потеря исходного спроса при шортаже** | Нулевые продажи из-за отсутствия товара превращаются в нулевую потребность → закупка не восстанавливает продажи, система «самоподтверждается» | Хранить `forecast_base` (исходный спрос) отдельно от `forecast_adapted` (реализуемый с учётом стока) и **никогда** не выводить потребность из фактических продаж. Потребность считается от исходного спроса |
| **Двойной учёт остатков при переключении уровней** | Один физический остаток попадает и в итог по магазину, и по категории, и по SKU | Единая гранулярность хранения (SKU × кабинет × склад/неделя), итоги — только производные агрегаты, никаких отдельных «таблиц итогов» |
| **Смешивание кабинетов WB** | Разные `chrtID`/баркоды у одного товара, разные остатки и цены | `shop_id` во всех таблицах фактов и интеграции, отдельный курсор синхронизации на кабинет, таблица сопоставления SKU с ручным разрешением конфликтов |
| **Формулы «переезжают» из Sheets и расходятся** | Никто не может сказать, какой расчёт правильный | Расчётное ядро — версионируемые чистые функции + эталонный набор тест-кейсов, согласованный со снабжением **до** реализации (golden dataset) |
| **Ручные правки затираются пересчётом** | Пользователь перестаёт доверять системе | Правки хранятся как отдельный слой (`override`) с автором, временем и причиной; пересчёт применяет их поверх базового расчёта, а не перезаписывает |
| **API WB: лимиты, дубли, дырки в истории** | Тихие пропуски → неверный прогноз | Идемпотентная загрузка по естественному ключу, курсоры, ретраи с backoff, журнал синхронизаций и алерты на пропуски |

## 2. Архитектура

```
        ┌──────────────────────────────────────────────────────────────┐
        │  Интеграции (воркеры)                                        │
        │  WB API: продажи, заказы, выкупы, остатки, поставки, цены     │
        │  курсор на кабинет · ретраи · дедупликация · журнал загрузок  │
        └───────────────┬──────────────────────────────────────────────┘
                        ▼
        ┌──────────────────────────────────────────────────────────────┐
        │  Хранилище (PostgreSQL)                                      │
        │  справочники: кабинеты, SKU-маппинг, категории, поставщики    │
        │  факты: недели продаж/заказов/выкупов/остатков/поставок       │
        │  план: базовый потенциал SKU, сезонность категорий,           │
        │        forecast_base, overrides, параметры закупки            │
        └───────────────┬──────────────────────────────────────────────┘
                        ▼
        ┌──────────────────────────────────────────────────────────────┐
        │  Расчётное ядро (сервер, чистые функции, версия алгоритма)    │
        │  недельная матрица · адаптированный прогноз/сток · DIFF       │
        │  OVER/SHORT · закупочная потребность (lead time, MOQ, PCB…)   │
        │  инкрементальный пересчёт зависимых недель по событию         │
        └───────────────┬──────────────────────────────────────────────┘
                        ▼
        ┌──────────────────────────────────────────────────────────────┐
        │  API (FastAPI) + UI                                          │
        │  один экран с переключателем уровня: магазины/категории/SKU   │
        │  редактирование и массовые правки, графики, журнал изменений  │
        └──────────────────────────────────────────────────────────────┘
```

**Принципы:**

1. **Все расчёты на сервере.** Браузер только отображает и редактирует. Иначе формулы разъедутся
   между клиентами, а «изменил прогноз → пересчиталось» станет невоспроизводимым.
2. **Факты неизменяемы, план версионируется.** Факты грузятся идемпотентно и не редактируются руками;
   плановые величины имеют историю версий (кто, когда, что и зачем изменил).
3. **Расчёт — детерминированная функция** `(факты, план, параметры, версия_алгоритма) → матрица`.
   Это даёт воспроизводимость («почему в понедельник было другое число») и возможность прогонять
   эталонные кейсы в CI.
4. **Пересчёт по событию, а не по таймеру.** Изменение прогноза/параметра ставит задачу
   на пересчёт затронутых SKU и недель (горизонт = lead time + coverage). Очередь — arq/Celery,
   задачи идемпотентны по ключу `(sku, неделя, версия)`.
5. **Агрегация — это GROUP BY, а не вторая таблица.** Уровни «магазин / категория / артикул»
   читают одну и ту же гранулярную витрину; двойной учёт исключён конструктивно.

### Технологии

* **Backend:** Python 3.12, FastAPI, SQLAlchemy 2.0, Alembic, Pydantic v2 — тот же стек, что в CheckStock.
* **БД:** PostgreSQL 17. Недельная матрица — обычная таблица фактов + материализованное
  представление витрины с инкрементальным обновлением; партиционирование по неделям, когда объём вырастет.
* **Фон:** arq (Redis) или Celery — синхронизация WB и пересчёты. Планировщик — те же воркеры.
* **UI:** прототип заказчика (HTML) доводится до SPA-компонента или серверного рендера —
  решаемо после аудита прототипа; критично сохранить один экран с переключателем уровня и быстрые массовые правки.
* **Наблюдаемость:** структурные логи, метрики синхронизаций (успех/лаг/пропуски), алерты,
  `/health`, `/invariants` (по аналогии с CheckStock).
* **Развёртывание:** Docker Compose на старте → managed PostgreSQL + бэкапы + CI/CD.

## 3. Модель данных (эскиз)

**Справочники**

* `shops` — кабинеты WB (все действующие одновременно; изоляция данных по `shop_id`).
* `products` — внутренний SKU (единая база товаров, цен, категорий, поставщиков).
* `product_mappings` — сопоставление внутреннего SKU с внешними ключами WB
  (`shop_id`, `seller_article`, `chrt_id`, `barcode`), статус сопоставления, конфликты на ручной разбор.
* `categories`, `suppliers`, `product_params` — lead time, MOQ, PCB (кратность упаковки),
  coverage, safety stock, целевой ROI, срок годности партии.

**Факты (гранулярность: кабинет × SKU × неделя)**

* `fact_sales`, `fact_orders`, `fact_buyouts`, `fact_stocks`, `fact_supplies` —
  естественный ключ `(shop_id, product_id, week_start[, source_id])`, что даёт идемпотентную загрузку.
* `sync_runs` — журнал загрузок: кабинет, тип данных, окно, курсор, количество, ошибки, длительность.

**План**

* `base_potential` — базовый потенциал SKU по неделям.
* `seasonality` — недельные коэффициенты категории (отдельная страница редактирования).
* `forecast_base` — исходный прогноз спроса (не зависит от наличия товара).
* `forecast_overrides` — ручные и массовые правки: автор, время, причина, область действия.
* `calc_versions` — версия алгоритма и параметры расчёта.

**Витрина (расчёт)**

* `weekly_matrix` — исходный и адаптированный прогнозы, реальный и адаптированный сток,
  факты, поставки, OVER/SHORT, DIFF, закупочная потребность, дата и объём заказа,
  версия расчёта и время пересчёта.

**Служебное**

* `audit_log` — журнал корректировок (требование ТЗ), `users`/`roles` — права доступа.

## 4. Расчётное ядро: как обеспечить «изменил прогноз → всё пересчиталось»

1. Прогноз спроса на неделю = базовый потенциал SKU × коэффициент сезонности категории ×
   поправки (акции, тренд) → `forecast_base`. Ручные правки ложатся слоем сверху.
2. `forecast_adapted` = min(исходный прогноз, доступный сток недели) — **реализуемые** продажи.
3. Реальный сток недели = остаток начала + поставки − продажи; адаптированный сток учитывает
   ограничение по доступности. OVER/SHORT и DIFF считаются по согласованным формулам заказчика.
4. Закупочная потребность считается **от `forecast_base`**, а не от продаж:
   спрос горизонта (lead time + coverage) + safety − доступный сток − уже заказанные партии,
   затем округление вверх до MOQ/PCB и проверка ROI. Дата заказа = дата потребности − lead time.
5. Пересчёт — только затронутых SKU и недель, транзакционно, с фиксацией версии алгоритма.

**Приёмка расчётов** (прямо из критериев ТЗ): statuses OVER/SHORT, DIFF и закупочные расчёты
совпадают с согласованными тест-кейсами. Предлагаю зафиксировать 20–40 эталонных недель
из текущих Sheets (вход → ожидаемый выход) и прогонять их в CI на каждом изменении ядра.
Это единственный способ безопасно «перенести формулы» и потом их менять.

**Что уже показано в CheckStock и переиспользуется здесь:** детерминированное ядро,
инварианты как самопроверка (`/api/invariants`), идемпотентные операции, версионируемая
история изменений, тесты на реальном PostgreSQL, включая случайные сценарии.

## 5. Интеграция с WB: что делает её стабильной

* **Курсор на кабинет и тип данных.** Каждая синхронизация продолжает с последнего успешного окна,
  а не «за последние N дней» — не будет дыр при падении.
* **Идемпотентность.** Запись по естественному ключу `(shop_id, product_id, week/day, source_id)`
  через upsert: повторная загрузка того же окна не создаёт дублей.
* **Лимиты и ретраи.** Токен-бакет на кабинет, экспоненциальный backoff, уважение `429`/`Retry-After`,
  разделение «тяжёлых» отчётов и быстрых справочников по расписанию.
* **Контроль качества.** После загрузки — сверки: сумма продаж по дням vs недельный агрегат,
  непустые остатки по каждому активному SKU, алерт при пропуске окна или падении объёма ниже порога.
* **Сопоставление SKU.** Автоматическое по баркоду/артикулу + очередь конфликтов на ручной разбор;
  несопоставленные позиции не теряются, а попадают в отчёт «требует внимания».
* **Изоляция кабинетов.** `shop_id` во всех запросах и таблицах, отдельные токены, отдельные курсоры;
  тест «данные кабинета A не попадают в итоги кабинета B» — обязательный в CI.
* **Расширение на Ozon / Яндекс Маркет** (вторая очередь): адаптер на площадку с общим интерфейсом
  `fetch_orders/fetch_stocks/fetch_supplies`, единая внутренняя модель фактов — новая площадка
  не меняет расчётное ядро.

## 6. Нефункциональные требования, которые стоит заложить сразу

* **Недели и таймзоны:** ISO-недели, единая таймзона расчёта (МСК), явное правило границы недели —
  иначе итоги разойдутся с Sheets на стыке недель.
* **Деньги:** `numeric`/копейки, никаких float; проценты и коэффициенты — с фиксированной точностью.
* **Права и аудит:** роли (снабжение, закупки, наблюдатель), журнал всех корректировок с автором и причиной.
* **Производительность:** витрина агрегируется на сервере, UI получает готовые срезы; целевой отклик
  переключения уровня — до 300 мс на горизонте 52 недели и текущем числе SKU.
* **Восстановление:** ежедневные бэкапы, проверка восстановления, миграции только вперёд с ревью.
* **Тестируемость:** эталонные кейсы расчётов, интеграционные тесты синхронизации на записанных
  ответах API (VCR), нагрузочный тест витрины.

## 7. Порядок работ и оценка

Оценка предварительная: уточняется после аудита прототипа и получения формул/эталонных кейсов.
Предполагается один разработчик full-time.

| Этап | Содержание | Оценка |
|---|---|---|
| 0. Технический аудит | разбор прототипа и Sheets, фиксация формул, эталонные кейсы, схема данных, план интеграции, доступы | 3–5 дней |
| 1. Каркас и справочники | репозиторий, CI, миграции, справочники SKU/категорий/поставщиков/кабинетов, маппинг SKU, права и аудит | 5–8 дней |
| 2. Интеграция WB | все действующие кабинеты: продажи, заказы, выкупы, остатки, поставки; курсоры, дедупликация, журнал, сверки | 8–12 дней |
| 3. Расчётное ядро | недельная матрица, адаптированный прогноз/сток, DIFF, OVER/SHORT, закупка (lead time, MOQ, PCB, coverage, safety, ROI), инкрементальный пересчёт | 10–15 дней |
| 4. Интерфейс | переключение уровней, редактирование и массовые правки, графики, журнал корректировок на базе прототипа заказчика | 8–12 дней |
| 5. Сверка и запуск | сверка с Sheets на эталонных неделях, приёмка, бэкапы, мониторинг, обучение, документация | 5–8 дней |
| **Итого** | **первая рабочая версия** | **~40–60 рабочих дней (8–12 недель)** |

Вторая очередь (Ozon, Яндекс Маркет, планирование оплат поставщикам) — оценивается отдельно,
архитектура к ней готова за счёт адаптеров площадок и общей модели фактов.

**Что нужно от заказчика на старте:** список кабинетов и токены WB, выгрузка текущих Sheets
с формулами, согласованные эталонные недели, правила статусов и DIFF, параметры закупки по SKU,
владелец решений по спорным формулам.

## 8. Что я предлагаю сделать в первые две недели

1. Зафиксировать формулы и эталонные кейсы (без этого любая реализация будет спорной).
2. Поднять каркас с CI и миграциями, завести справочники и маппинг SKU.
3. Подключить **один** кабинет WB полностью (продажи + остатки + поставки) и показать сверку с Sheets
   на 4 неделях — это снимает главный риск проекта раньше, чем будет написан весь интерфейс.
4. Параллельно — технический аудит прототипа UI: что переиспользуем, что переписываем.

Такой порядок даёт заказчику проверяемый результат на второй неделе и не оставляет
интеграционные сюрпризы на конец проекта.
