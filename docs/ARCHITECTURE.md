# Архитектура CheckStock

Документ отвечает на вопрос «как устроен учёт и почему именно так».
Краткая версия с обоснованиями — в [README](../README.md), раздел 3.

## 1. Модель данных

| Таблица | Назначение | Важные ограничения |
|---|---|---|
| `shops` | магазин (в тестовых данных один) | уникальное имя |
| `warehouses` | склад фулфилмента (ФФ) | `archived_at` вместо удаления; партиальный уникальный индекс `lower(name)` среди активных |
| `products` | артикул (SKU) | уникальный `sku` |
| `locations` | **узел учёта**: где числится товар | kind ∈ supplier / fulfillment / transit / marketplace / client; по одному узлу на ФФ и на документ в пути; singleton-узлы защищены партиальным индексом |
| `documents` | приход, перемещение, FBS-заказ, FBO-поставка | `CHECK` на kind и status |
| `document_lines` | строки документа | `qty > 0`, уникальность (документ, артикул) |
| `document_events` | факт перехода статуса | уникальный `idempotency_key`, `response_snapshot` для повтора |
| `ledger_entries` | **проводки**, append-only | `qty_delta <> 0`, триггер запрещает UPDATE/DELETE |
| `stock_balances` | остатки = проекция журнала | PK (артикул, узел, карман), триггер запрещает минус |

Карманы (`bucket`): `free` — доступно, `reserved` — резерв FBS. Оба существуют только на узлах-ФФ;
остальные узлы используют `free`.

**Физически на ФФ** = `free + reserved`. **Доступно** = `free`.

## 2. Проводки по каждому переходу

Обозначения: `ФФᶠ` — карман «доступно», `ФФʳ` — карман «резерв», `T(doc)` — узел «в пути» документа.

| Документ | Переход | Проводки (на каждую строку qty = q) |
|---|---|---|
| Приход | `draft → posted` | `Поставщик −q`, `ФФ-получательᶠ +q` |
| Перемещение | `draft → shipped` | `ФФ-отправительᶠ −q`, `T(doc) +q` |
| Перемещение | `shipped → received` | `T(doc) −q`, `ФФ-получательᶠ +q` |
| Перемещение | `draft → cancelled` | проводок нет (товар не двигался) |
| FBS | `создание → reserved` | `ФФᶠ −q`, `ФФʳ +q` |
| FBS | `reserved → shipped` | `ФФʳ −q`, `T(doc) +q` |
| FBS | `shipped → delivered` | `T(doc) −q`, `Клиент +q` |
| FBS | `reserved → cancelled` | `ФФʳ −q`, `ФФᶠ +q` |
| FBO | `draft → shipped` | `ФФᶠ −q`, `T(doc) +q` |
| FBO | `shipped → received` | `T(doc) −q`, `Склад МП +q` |

Сумма проводок по каждому артикулу внутри события всегда 0 — это проверяется в
`app/accounting.py::apply_postings` до записи и инвариантом `ledger_balanced` после.

## 3. Конечные автоматы

```
Приход:       draft ──post──> posted
Перемещение:  draft ──ship──> shipped ──receive──> received
                └──cancel──> cancelled
FBS-заказ:    reserved ──ship──> shipped ──deliver──> delivered
                └──cancel──> cancelled
FBO:          draft ──ship──> shipped ──receive──> received
                └──cancel──> cancelled
```

Всё, что не перечислено в `app/documents.py::TRANSITIONS`, запрещено и возвращает `409`.
Отмена возможна только до отправки: после отправки товар физически покинул склад,
и «отменить» его — значит потерять груз. Возврат оформлялся бы отдельным документом.

## 4. Транзакции и конкурентность

* Один HTTP-запрос = одна сессия = одна транзакция (`app/db.py::get_session`):
  успех → `commit`, любое исключение → `rollback`. Частично применённых проводок не бывает.
* Документ читается `SELECT … FOR UPDATE` — параллельные переходы одного документа сериализуются.
* Строки остатков блокируются в детерминированном порядке `(артикул, узел, карман)`:
  одинаковый порядок во всех операциях исключает взаимные блокировки.
* Проверка достаточности выполняется **под блокировкой**, а не до неё, поэтому два
  параллельных резерва не могут вместе превысить остаток.
* `lock_timeout = 10s`, `statement_timeout = 60s` на соединении: лучше внятная ошибка, чем зависший запрос.
* Идемпотентность: сначала ищем событие по `Idempotency-Key` (возвращаем снимок ответа),
  затем блокируем документ и проверяем автомат. Уникальный индекс по ключу страхует гонку
  на разных документах — срабатывает `409 CONFLICT`.

## 5. Инварианты (`GET /api/invariants`)

| Имя | Что означает |
|---|---|
| `ledger_balanced` | сумма проводок по каждому артикулу = 0 |
| `projection_matches_ledger` | остатки = сумма журнала (full outer join, ловит и лишние, и недостающие строки) |
| `no_negative_stock` | ни один узел, кроме поставщика, не в минусе |
| `transit_matches_documents` | на узле «в пути» ровно содержимое отправленного и не принятого документа |
| `reserved_matches_fbs` | резерв ФФ = сумма строк активных FBS-заказов |

Дополнительно в тестах: `приход = ФФ + в пути + склад МП + у клиента` по каждому артикулу.

## 6. Чтение модели: экран остатков и «где числится»

`app/queries.py` читает проекцию с join'ом на узлы, склады и документы. Подписи мест
(«Север · доступно», «В пути между ФФ: Север → Юг (док. #7)») строятся **из текущих данных**,
поэтому переименование склада мгновенно отражается в остатках, в пути и в истории —
никаких денормализованных строк, которые могут разойтись.

Архивный ФФ попадает в матрицу остатков, если на нём что-то числится (или включён флаг
«показывать архивные»). Пустые архивные склады скрыты, чтобы не шуметь.

## 7. API

Все ошибки: `{"error": {"code", "message", "details"}}`. Коды: `404 NOT_FOUND`,
`409 CONFLICT`, `409 INSUFFICIENT_STOCK`, `422 VALIDATION_FAILED`.
Все мутации принимают заголовок `Idempotency-Key`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/health`, `GET /api/meta` | здоровье и справочники для UI |
| `GET /api/stock?search=&include_archived=` | матрица остатков |
| `GET /api/stock/{sku}/where` | где числится артикул |
| `GET/POST /api/warehouses`, `PATCH/DELETE /api/warehouses/{id}` | ФФ; DELETE = архив |
| `POST /api/warehouses/{id}/restore`, `GET /api/warehouses/{id}/stock` | восстановление, что лежит |
| `GET/POST /api/products` | артикулы |
| `POST /api/receipts`, `POST /api/receipts/{id}/post` | приход |
| `POST /api/transfers`, `…/{id}/ship`, `…/{id}/receive`, `…/{id}/cancel` | перемещение |
| `POST /api/transfers/quick` | создать + отправить + принять одной транзакцией |
| `POST /api/fbs/orders` (`allow_split`), `…/{id}/ship`, `…/{id}/deliver`, `…/{id}/cancel` | FBS |
| `POST /api/fbo/shipments`, `…/{id}/ship`, `…/{id}/receive`, `…/{id}/cancel` | FBO |
| `GET /api/documents`, `GET /api/history` | документы и журнал с фильтрами |
| `GET /api/invariants`, `POST /api/demo/reset` | самопроверка и сброс демо-данных |

Полная интерактивная схема — `/docs`.
