# Как проверить CheckStock

## 1. Автотесты

```bash
docker compose exec app pytest -q                       # всё, ~20 секунд
docker compose exec app pytest -m "not slow" -q          # без конкурентности и случайных сценариев
docker compose exec app pytest --cov=app --cov-report=term-missing
docker compose exec app ruff check app tests scripts
```

Тесты идут против **реального PostgreSQL**: отдельная база `checkstock_test` создаётся
автоматически, схема накатывается теми же миграциями Alembic. Перед каждым тестом база
очищается и заполняется тестовыми данными из ТЗ. Данные рабочей базы не затрагиваются.

### Карта тестов по критериям ТЗ

| Критерий | Файл | Что именно проверяется |
|---|---|---|
| Учёт после прихода | `test_receipts.py` | черновик не двигает товар; проведение добавляет ровно один раз; повтор = 409; повтор с ключом = тот же ответ; история «Поставщик → Север · доступно» |
| Учёт после резерва и отправки FBS | `test_fbs.py` | резерв блокирует, но не убирает товар физически; отправка списывает резерв и уводит «в пути к клиенту»; доставка; отмена возвращает; резерв недоступен другим заказам и FBO |
| Учёт после перемещения | `test_transfers.py` | отправка → «в пути между ФФ», приёмка → на складе; приёмка до отправки запрещена; повторная приёмка не удваивает; отмена черновика; отмена отправленного запрещена |
| Учёт после FBO | `test_fbo.py` | товар покидает ФФ, числится в пути, после приёмки — на складе МП; повторная приёмка; нехватка |
| Нехватка при достаточном общем остатке | `test_shortage.py` | раскладка (нужно/есть/всего/другие ФФ), план перемещения, план разбивки, закрытие дефицита перемещением, разбивка на два отправления с одним номером заказа, отказ когда не хватает везде, мультистрочная разбивка |
| Удаление ФФ с остатком | `test_warehouse_delete.py` | остатки и резерв сохранены; склад виден в матрице и «где числится»; история цела; новые документы запрещены; начатые можно завершить; архив идемпотентен; имя освобождается; восстановление и конфликт имён |
| Повторное подтверждение | `test_idempotency.py` | тот же ключ → тот же ответ и одно событие; без ключа → 409; идемпотентное создание приход/заказ/разбивка; ключ нельзя переиспользовать для другого документа |
| Конкурентность | `test_concurrency.py` | 5 параллельных отправок → ровно один успех; 6 параллельных резервов по 2 шт при остатке 5 → остаток не в минусе; параллельные запросы с одним ключом → одно списание |
| Сходимость после каждого действия | все файлы + `test_random_scenarios.py` | `assert_invariants()` после каждого шага; 150 случайных операций (приход, перемещения, резервы, отмены, разбивки, переименования, архивирование) и финальная пересборка проекции из журнала |
| Целостность модели | `test_accounting.py` | несбалансированные проводки отвергаются; нулевая проводка отвергается; нельзя списать больше остатка; проекция пересобирается из журнала; триггеры БД запрещают изменение журнала и минус на складе |
| HTTP и интерфейс | `test_api_smoke.py` | страница и статика отдаются, `/docs` и OpenAPI живы, фильтры документов/истории, формат ошибок, сброс демо-данных возвращает данные из ТЗ |

## 2. Сквозной сценарий одной командой

```bash
make doctor      # контейнеры + API + пять инвариантов
make demo        # сквозной сценарий; внутри контейнера API всегда на 8000
```

Скрипт прогоняет 11 шагов (приход → резерв → отправка → повтор → доставка → FBO →
нехватка → перемещение → разбивка → перемещение по шагам → удаление ФФ) и **сам себя проверяет**:
после каждого шага сверяет «принято = числится» и вызывает инварианты. Ненулевой код возврата = провал.
Начинается со сброса демо-данных.

## 3. Ручной чек-лист в интерфейсе (5 минут)

Открой http://localhost:18080 (или свой `APP_PORT` из `.env`) и нажми «Сбросить демо-данные».

1. **Остатки.** SKU-101: Север 10/10/0, Юг 6/6/0 (физ./дост./резерв). SKU-102: 5 и 0. SKU-103: 0 и 4.
   Бейдж в шапке — «✓ Остатки сходятся».
2. **Резерв.** Операции → FBS-заказ: Север, SKU-101, 4 шт, номер WB-1001 → «Зарезервировать».
   В остатках: Север **10 / 6 / 4** — физически не изменилось, доступно упало, резерв вырос.
3. **Отправка.** В списке документов у заказа WB-1001 → «Отправить клиенту».
   Север: 6/6/0, колонка «в пути к клиенту (FBS)» = 4.
4. **Повтор.** Кнопка «Повтор ×2» у любого документа с действием: первый запрос 200,
   второй 200 (повтор), третий без ключа 409. Остатки не изменились, бейдж зелёный.
5. **Доставка.** «Доставлен» → «в пути» = 0, «У клиента» = 4.
6. **FBO.** Операции → FBO: Север, SKU-102, 3 шт → создать → «Отправить на МП» →
   колонка «в пути на МП (FBO)» = 3, Север 2 → «Принято на МП» → «Склад МП» = 3.
7. **Нехватка.** FBS: Север, SKU-101, 12 шт → «Зарезервировать». Появится окно:
   нужно 12, на Севере 6, всего 12, план «переместить 6 с Юга» и план разбивки.
   Нажми **«Переместить и повторить»** — заказ пройдёт, в истории будет три события перемещения.
8. **Разбивка.** FBS: Север, SKU-102, 4 шт, галочка «разрешить разбить по складам» →
   два отправления с одним номером заказа.
9. **Перемещение по шагам.** Операции → Перемещение: Север → Юг, SKU-101, 2 шт, без галочки «сразу» →
   «Отправить» (появится «в пути между ФФ» = 2) → «Принять» (Юг +2).
10. **Удаление ФФ с остатком.** Склады → «Удалить (в архив)» у Юга. В окне видно, что на нём лежит.
    После подтверждения: склад помечен «архив», остатки и резерв на месте, в «где числится»
    строка «Юг (архивный ФФ)», история цела. Попробуй создать приход на Юг — получишь отказ.
11. **Переименование.** Переименуй Север → «Север-2»: имя обновится в остатках, в пути и в истории.
12. **История.** Вкладка «История»: по каждому событию видно артикул, количество, откуда и куда.

## 4. Проверка через API (curl)

Примеры с хоста: порт `18080` (или свой `APP_PORT`). Внутри контейнера — `8000`.

```bash
# Нехватка с раскладкой
curl -s -X POST localhost:18080/api/fbs/orders -H 'Content-Type: application/json' \
  -d '{"from_warehouse_id":1,"lines":[{"sku":"SKU-101","qty":12}],"reference":"WB-1"}' | jq

# Идемпотентное проведение прихода
curl -s -X POST localhost:18080/api/receipts -H 'Content-Type: application/json' \
  -d '{"to_warehouse_id":1,"lines":[{"sku":"SKU-101","qty":5}]}' | jq .id
curl -s -X POST localhost:18080/api/receipts/3/post -H 'Idempotency-Key: my-key-1' | jq .status
curl -s -X POST localhost:18080/api/receipts/3/post -H 'Idempotency-Key: my-key-1' -D- | head -1

# Сходимость
curl -s localhost:18080/api/invariants | jq '.ok, .checks[].name'

# Где числится товар
curl -s localhost:18080/api/stock/SKU-101/where | jq '.positions[] | {label, qty}'
```

## 5. Что смотреть в базе

```bash
make psql
```

```sql
-- журнал проводок последнего события
SELECT * FROM ledger_entries ORDER BY id DESC LIMIT 10;

-- остатки по узлам
SELECT p.sku, l.kind, l.name, b.bucket, b.qty
FROM stock_balances b
JOIN products p ON p.id = b.product_id
JOIN locations l ON l.id = b.location_id
WHERE b.qty <> 0 ORDER BY p.sku, l.kind;

-- сумма проводок по артикулу должна быть 0
SELECT p.sku, SUM(e.qty_delta) FROM ledger_entries e
JOIN products p ON p.id = e.product_id GROUP BY p.sku;
```
