# CheckStock — «где сейчас товар»

[![CI](https://github.com/TomRusski/checkstock/actions/workflows/ci.yml/badge.svg)](https://github.com/TomRusski/checkstock/actions/workflows/ci.yml)

Прототип учёта остатков по складам фулфилмента (ФФ): сколько физически лежит, сколько доступно,
сколько заблокировано резервом FBS, что едет между ФФ, на склад маркетплейса (FBO) и к клиенту (FBS).

**Стек:** Python 3.12 · FastAPI · PostgreSQL 17 · SQLAlchemy 2.0 · Alembic · Jinja2 + ванильный JS (без сборки) · pytest · Docker Compose.

---

## 1. Запуск за три команды

```bash
cp .env.example .env          # необязательно: значения по умолчанию уже подходят
docker compose up -d --build
# открыть http://localhost:18080
```

Что произойдёт автоматически: поднимется PostgreSQL 17, накатятся миграции Alembic,
база заполнится тестовыми данными из ТЗ (магазин, ФФ «Север» и «Юг», три артикула, проведённый приход).

| Адрес | Что там |
|---|---|
| **http://localhost:18080** | интерфейс |
| http://localhost:18080/docs | Swagger: все эндпоинты можно дёргать руками |
| localhost:**15432** | PostgreSQL (user/pass/db: `checkstock`) |

Порты **18080** и **15432** выбраны нестандартными специально: они не пересекаются ни с обычным
PostgreSQL (5432/5433), ни с типовыми dev-серверами (8000/8080/3000).

### Если порт всё-таки занят

Симптом: `Bind for 127.0.0.1:15432 failed: port is already allocated`.
Лечится одной строкой в `.env` — код и compose менять не нужно:

```bash
cp .env.example .env
printf 'DB_PORT=15433\nAPP_PORT=18081\n' >> .env   # любые свободные порты
docker compose up -d
make ports                # показать, какие порты реально применились
```

**Важно понимать разницу:** в паре `"18080:8000"` слева порт **на хосте** (его открывает браузер),
справа — порт **внутри контейнера**. Внутри контейнера приложение всегда слушает `8000`,
а в docker-сети ходит в `db:5432`. Поэтому:

* из браузера/с хоста — `http://localhost:18080` (или твой `APP_PORT`);
* внутри контейнера (`docker compose exec app …`) — `http://localhost:8000`;
* `make demo`, `make invariants`, `make doctor` уже используют правильный внутренний адрес.

### Проверка, что всё живо

```bash
make doctor                           # контейнеры + API + сходимость остатков
docker compose exec app pytest        # 76 тестов, ~20 секунд
make demo                             # сквозной сценарий из ТЗ с самопроверкой
```

Полезные команды: `make ports`, `make logs`, `make seed` (пересоздать тестовые данные),
`make test-cov`, `make lint`, `make psql`, `make reset-db` (полностью чистая база).

## 2. Что смотреть в интерфейсе

* **Остатки** — матрица «артикул × ФФ»: физически / доступно / резерв, плюс три отдельных
  колонки «в пути» (между ФФ, на МП по FBO, к клиенту по FBS), склад маркетплейса и «у клиента».
  Клик по артикулу → **«где числится товар»**: разложение по всем местам, включая архивные ФФ
  и конкретные документы в пути.
* **Склады** — добавить, переименовать, удалить (в архив), восстановить, посмотреть что лежит.
* **Операции** — приход, перемещение, FBS-заказ, FBO-поставка и список документов с кнопками
  по статусам. Кнопка **«Повтор ×2»** отправляет одно подтверждение трижды и показывает,
  что списание произошло один раз.
* **История** — какой товар, сколько единиц, откуда и куда переместился.
* **Бейдж в шапке** — живая проверка сходимости учёта (`GET /api/invariants`).

Сценарий для быстрой проверки описан в [docs/TESTING.md](docs/TESTING.md),
подробности модели — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## 3. Ключевые решения

### 3.1. Остатки — не поля с числами, а проекция журнала двойной записи

Соблазнительный вариант — таблица `stock(warehouse_id, sku, qty, reserved)` и `UPDATE qty = qty - n`.
Он ломается на первом же «товаре в пути»: непонятно, где числится груз между отправкой и приёмкой,
а любая ошибка в коде тихо теряет товар.

Поэтому в основе — **журнал проводок** (`ledger_entries`, append-only) и **узлы учёта** (`locations`):

```
Поставщик ──приход──> ФФ.доступно ──резерв──> ФФ.резерв ──отправка FBS──> В пути к клиенту ──> Клиент
                          │                                                    
                          ├──отправка перемещения──> В пути между ФФ ──приёмка──> другой ФФ.доступно
                          └──отправка FBO─────────> В пути на МП ────приёмка──> Склад маркетплейса
```

Любая операция — набор проводок, **сумма которых по каждому артикулу равна нулю**.
Приход: `Поставщик −10 / Север +10`. Отправка перемещения: `Север.доступно −3 / В пути +3`.
Приёмка: `В пути −3 / Юг.доступно +3`.

Отсюда главное свойство: **«остатки сходятся» проверяется одной SQL-проверкой**, а не глазами.
`GET /api/invariants` считает пять инвариантов, тесты вызывают их после каждого действия:

1. сумма проводок по артикулу = 0 (товар не появляется и не исчезает);
2. остатки в точности равны сумме журнала;
3. ни один узел, кроме поставщика, не в минусе;
4. «в пути» = ровно то, что отправлено и ещё не принято;
5. резерв на ФФ = сумма активных FBS-заказов.

Остатки (`stock_balances`) — материализованная проекция: её можно удалить и пересобрать из журнала
(`app/accounting.py::rebuild_projection`), тест проверяет, что получится то же самое.

### 3.2. Резерв FBS — это карман внутри склада, а не отдельный остаток

`Физически = доступно + резерв`. Резервирование не уводит товар со склада: проводка
`ФФ.доступно −4 / ФФ.резерв +4`. Поэтому в таблице «физически» не меняется, «доступно» падает,
«резерв» растёт — ровно то, что видит менеджер. Отправка FBS списывает **резерв**, а не свободный
остаток, отмена заказа возвращает товар в «доступно». Товар, зарезервированный под заказ,
недоступен ни другому FBS-заказу, ни перемещению, ни FBO — это проверяется тестами.

### 3.3. «В пути» — отдельный узел на каждый документ

Товар в пути не «висит в воздухе»: у каждого отправленного документа свой узел учёта.
Поэтому видно не только «4 штуки где-то едут», а «4 штуки едут с Севера на Юг по документу №7».
Три потока (между ФФ / на МП / к клиенту) различаются типом документа и не смешиваются в одну колонку.

### 3.4. Повторное подтверждение не списывает товар дважды — два уровня защиты

* **Конечный автомат документа.** Переход разрешён только из конкретного статуса
  (`draft → shipped → received`). Повторный `POST /ship` получает `409 CONFLICT` и не пишет проводок.
* **Idempotency-Key.** Если клиент передал ключ, ответ сохраняется в событии документа
  (`document_events.response_snapshot`, уникальный индекс по ключу). Повтор с тем же ключом
  возвращает **тот же ответ** с заголовком `Idempotency-Replayed: true` — удобно для ретраев
  при таймауте, когда клиент не знает, дошёл ли первый запрос.
* **Блокировки строк.** Документ берётся `SELECT … FOR UPDATE`, строки остатков блокируются
  в детерминированном порядке (по артикулу, узлу, карману) — параллельные подтверждения
  сериализуются и не устраивают deadlock. Тест `test_concurrency.py` бьёт пятью параллельными
  запросами и проверяет, что успех ровно один, а остаток не ушёл в минус.

### 3.5. Удаление ФФ — архивирование, а не `DELETE`

ТЗ требует сохранить остатки и историю. Физическое удаление строки склада уничтожило бы и то,
и другое (или потребовало бы «висячих» ссылок). Поэтому `DELETE /api/warehouses/{id}` ставит
`archived_at`:

* остатки и история остаются, склад виден в матрице остатков с пометкой «архив»
  и в «где числится товар» — товар нельзя спрятать удалением склада;
* новые документы на архивный ФФ запрещены (`409`);
* **начатые документы можно довести до конца** — иначе товар навсегда завис бы в пути
  или в резерве на несуществующем складе;
* имя освобождается: можно создать новый «Юг», старые остатки останутся на старом узле;
* есть восстановление (`POST /warehouses/{id}/restore`), архивирование идемпотентно.

### 3.6. Нехватка на выбранном ФФ при достаточном общем остатке

Это не ошибка «500» и не сухой отказ. API возвращает `409 INSUFFICIENT_STOCK` с раскладкой:
сколько нужно, сколько есть на выбранном ФФ, сколько всего по сети, что лежит на других ФФ,
и **два готовых плана**:

```json
{"error": {"code": "INSUFFICIENT_STOCK",
  "message": "На складе «Север» доступно 10 шт SKU-101, нужно 12. Всего по сети доступно 16 шт …",
  "details": {"requested": 12, "available_on_warehouse": 10, "shortfall": 2, "total_available": 16,
    "transfer_plan": [{"from_name": "Юг", "to_name": "Север", "qty": 2}],
    "split_plan": [{"name": "Север", "qty": 10}, {"name": "Юг", "qty": 2}]}}}
```

Интерфейс показывает эти варианты кнопками:

1. **«Переместить и повторить»** — создаёт перемещение и проводит его целиком
   (`POST /api/transfers/quick` = создать + отправить + принять **одной транзакцией**,
   в журнале остаются три честных события), затем повторяет заказ.
2. **«Разбить по складам»** — `allow_split: true`: заказ раскладывается по ФФ
   (сначала выбранный), создаются несколько отправлений с одним номером заказа.
3. **Отказ** — если товара не хватает даже суммарно, планы пустые и предлагается приход.

### 3.7. Часть гарантий вынесена в саму PostgreSQL

Код приложения может быть обойдён (скрипт, ручной SQL, будущий сервис), поэтому:

* триггер запрещает `UPDATE`/`DELETE` в `ledger_entries` — журнал только дополняется;
* триггер запрещает отрицательный остаток на любом узле, кроме поставщика;
* `CHECK` на количество, тип документа, статус, карман;
* партиальный уникальный индекс: имя склада уникально среди **активных** складов магазина;
* партиальный уникальный индекс на singleton-узлы (поставщик, маркетплейс, клиент);
* `lock_timeout`/`statement_timeout` на соединении — запрос не висит вечно.

Оба триггера проверяются тестами через прямой SQL.

### 3.8. Синхронный стек — осознанный выбор

SQLAlchemy 2.0 + psycopg3 в синхронном режиме, эндпоинты — обычные `def`.
Учётная логика — это транзакции и блокировки; в синхронном виде её проще читать, отлаживать
и объяснять. FastAPI выполняет такие эндпоинты в threadpool, параллельные запросы обрабатываются
нормально (что и проверяет тест конкурентности). Async здесь не дал бы выигрыша: узкое место — БД.

### 3.9. Фронтенд без сборки

Одна HTML-страница, один CSS, один JS-файл, всё отдаёт тот же FastAPI. Ни npm, ни бандлера,
ни CORS, ни второго контейнера. Клиент не «додумывает» остатки: после каждой мутации данные
перезагружаются с сервера. Для прототипа на один день это максимум проверяемости при минимуме движущихся частей.

## 4. Как проверялся результат

```bash
docker compose exec app pytest -q                      # 76 тестов
docker compose exec app pytest --cov=app               # покрытие 95%
docker compose exec app ruff check app tests scripts   # линтер
make demo                                              # сквозной сценарий против сервера
```

Тесты идут **против настоящего PostgreSQL** (не SQLite): проверяются блокировки, триггеры,
партиальные индексы. Карта тестов и ручной чек-лист — [docs/TESTING.md](docs/TESTING.md).

| Что проверяем | Чем |
|---|---|
| Учёт после прихода, резерва, перемещения, отправки, приёмки | `test_receipts.py`, `test_transfers.py`, `test_fbs.py`, `test_fbo.py` |
| Нехватка при достаточном общем остатке | `test_shortage.py` (отказ с раскладкой, перемещение, разбивка, мультистроки) |
| Удаление ФФ с остатком | `test_warehouse_delete.py` (остатки, история, запрет новых операций, завершение начатых, имя, восстановление) |
| Повторное подтверждение | `test_idempotency.py`, `test_concurrency.py` (5 параллельных запросов) |
| Сходимость после **каждого** действия | `assert_invariants()` во всех тестах + `test_random_scenarios.py`: 150 случайных операций |
| Целостность самой модели | `test_accounting.py`: несбалансированные проводки, пересборка проекции, триггеры БД |
| Интерфейс | сквозной прогон в headless-браузере: все вкладки, модалка нехватки, кнопки документов, «Повтор ×2», ноль ошибок в консоли |

## 5. Ограничения прототипа (что бы я сделал дальше)

Сознательно не делал, чтобы уложиться в день и не размывать учётное ядро:

* **Приёмка целиком.** Частичная приёмка и расхождения (недовоз/излишки) — следующий шаг:
  в модели уже есть событие и проводки, добавляются `received_qty` и проводка расхождения.
* **Возвраты от клиента и с МП** — обратные документы, узлы уже позволяют это выразить.
* **Один магазин и один маркетплейс** в тестовых данных; `shop_id` в схеме есть, мультимагазин
  включается фильтрами и правами.
* **Нет авторизации и ролей** — прототип открыт; в бою: OIDC/сессии, роли «менеджер / кладовщик / аудитор»,
  журнал действий уже есть (`document_events`).
* **Отмена отправки** запрещена (товар в пути надо принять). В бою — документ возврата с проводками.
* **Резерв под FBS без TTL.** В бою — автоотмена просроченного резерва фоновой задачей.
* **UI без пагинации** (лимит 100 документов) и без веб-сокетов: обновление по кнопке/после действия.

## 6. Использование ИИ и проверка результата

ИИ использовался как ускоритель: каркас FastAPI-приложения, шаблон миграции, boilerplate
форм и таблиц интерфейса, черновики тестов. Технические решения принимались и проверялись вручную:

* модель учёта (узлы + двойная запись), правила резерва, архивирования и нехватки — спроектированы
  до кода и зафиксированы в разделе 3 и в `docs/ARCHITECTURE.md`;
* каждый сценарий из ТЗ проверен тестом на реальном PostgreSQL, включая параллельные подтверждения
  и 150 случайных операций с проверкой инвариантов после каждого шага;
* найдено и исправлено руками, а не «сгенерировано заново»: зависание `TRUNCATE` из-за открытой
  транзакции (добавлен `lock_timeout`), ошибка CSS, из-за которой скрытая модалка перехватывала клики
  (проверено прогоном интерфейса в headless-браузере), неверные ожидания в тестах арифметики остатков.

## 7. Структура проекта

```
app/
  models.py       — схема: узлы, документы, события, журнал, остатки
  accounting.py   — ядро: проводки, блокировки, пересборка проекции
  documents.py    — конечный автомат + проводки для каждого перехода
  services.py     — приход / перемещение / FBS (в т.ч. разбивка) / FBO
  allocation.py   — нехватка: раскладка по складам и планы действий
  catalog.py      — магазин, ФФ (архив вместо удаления), артикулы
  queries.py      — экран остатков, «где числится», история
  invariants.py   — пять проверок сходимости
  api.py          — HTTP-эндпоинты, единый формат ошибок
  seed.py         — тестовые данные из ТЗ
  templates/, static/ — интерфейс без сборки
migrations/       — Alembic: схема + триггеры гарантий
tests/            — 76 тестов на реальном PostgreSQL
scripts/          — сквозное демо и проверка инвариантов
docs/             — архитектура, тестирование, предложение по системе снабжения
```
